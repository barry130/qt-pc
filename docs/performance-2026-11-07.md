# qt-pc 性能检查（2026-11-07）

本轮确认并修复了大歌单收藏查重阻塞界面的问题，并停止无时间轴文字稿的无效播放计时更新。当前开发版短时 CPU 占用较低，内存主要分布在 WebView 和 GPU 进程。本机 base 识别及轻量英译中有跟上短段播放的计算余量；首次音频缓存、识别质量和完整应用调度仍会影响字幕延迟。

## 环境与测量范围

- Windows；AMD Ryzen 7 6800H，8 核 / 16 逻辑处理器；Node 25.9.0。
- 进程采样针对已运行的 `tauri dev` 及其所属 WebView 子进程，20 秒、5 次采样。未控制用户当时播放状态，不将其称为“空闲”或标准播放场景。
- 没有停止开发程序、修改个人配置或读写真实歌单。收藏基准使用确定性合成元数据；音频使用上游公开 `jfk.wav`；翻译使用自编英文。
- 以下为本机观测值，不是发行版资源承诺、长时间泄漏结论或跨设备指标。Node 事件循环的间隔测量也不等同于 WebView 帧率。

## 收藏查重修复

原实现对每一首新增歌曲重新合并整个候选数组，并反复归一化所有候选的歌名、歌手和专辑。即使歌名明显不可能相似，仍完整计算三类编辑距离，全部同步占用界面线程。

现在每次检查只准备一次元数据和索引。歌名长度差、字符计数差用于排除不可能达到最低阈值的项，最后仍调用原有共享匹配规则；PC 和移动端的阈值及规则文件保持一致。存在判断使用 `Set`。单曲收藏、批量收藏和新建歌单入口共用约 8ms 的协作分片，关闭面板或改变选择会取消后续计算；回到界面前再次校验账号。分片预算是调度目标，GC、异常长元数据等仍可能延长个别片段。

| 已有 / 新增曲目 | 修复前同步检查 | 修复后同步核心 | 修复后界面异步入口 | 异步时最长定时器间隔 |
| --- | ---: | ---: | ---: | ---: |
| 200 / 1 | 7.7ms | 3.4ms | 2.5ms | 2.6ms |
| 1000 / 50 | 585ms | 41ms | 44ms | 9.4ms |
| 5000 / 100 | 5092ms | 402ms | 472ms | 11.4ms |
| 10000 / 200 | 21401ms | 1532ms | 1895ms | 11.9ms |

这是固定随机种子的四组单次结果，存在 JIT、CPU 调度和缓存波动。另一次同时运行识别测试时，最后一组异步耗时约 3.3 秒、最长定时器间隔约 14ms。不要把小规模同步/异步结果差异解释为异步本身更快。算法仍需检查候选组合；字符相同但顺序不同、超多同名歌曲等输入的收益会较小。

复现：`node scripts/benchmark-collection.mjs`。脚本在内存中打包真实生产入口，输出耗时和事件循环间隔；可传入保留的旧版模块路径做对照。1ms 心跳用于检查是否能让出线程，不是产品中的常驻定时器。

验证包含 30 组共享匹配向量、Unicode/短名称/长名称边界、桥接分组顺序、一次归一化、中途取消，以及三个界面入口在异步返回后不再写入失效选择。另将 1000/50、5000/100 的完整计划与保存的旧实现逐项比较，结果一致；移动端现有一致性检查通过。

## 播放与文字稿

播放位置已有 100ms 定时推进、暂停停表和高频组件隔离；歌词行有 memo，播客正文最多渲染 200 条。无需把整页恢复成每帧更新。

本轮为 `useInterpolatedPosition` 增加可停用订阅：无时间轴文字稿既不启动插值定时器，也不响应位置锚点更新。切换回同步字幕时立即对齐当前播放位置，恢复原有定时推进。回归测试验证定时器清理、锚点更新不重渲染及重新启用。

生产前端构建仍按页面拆分，主要文件未压缩 / gzip：主窗口约 447 / 146 kB，入口约 300 / 93 kB，播放页约 71 / 23 kB。未发现需要为此引入新的打包方案的证据。

## 本地识别与翻译实测

使用已安装的官方 b5454 Windows x64 CPU 引擎；`-t 4 -ng -mc 0` 与当前应用配置一致。每轮启动独立进程，耗时包含进程启动、模型加载、识别与 JSON 输出，不含应用音频下载、压缩音频解码、字幕入库与重绘。

| 工作 | 三次墙钟耗时 |
| --- | --- |
| tiny，11 秒公开英文音频，指定 en | 1.16 / 0.79 / 0.78 秒 |
| base，11 秒公开英文音频，指定 en | 1.77 / 1.29 / 1.32 秒 |
| base，22 秒音频，自动语言 | 2.94 / 2.51 / 2.47 秒 |
| Argos 英译中，3 句合成英文 | 0.63 / 0.59 / 0.66 秒 |
| Argos 英译中，12 句合成英文 | 1.30 / 1.19 / 1.07 秒 |
| 翻译进程加载模型但输入为空（启动开销对照） | 0.63 / 0.39 / 0.36 秒 |

22 秒输入由公开 11 秒样本重复拼接，仅用于固定时长的吞吐测试，不代表多语种播客质量测试。所有推理退出码为 0。翻译使用现有 CTranslate2 4.8.5 / int8 / 4 线程 / beam 2，没有改用大型聊天模型。

22 秒片段耗时约 2.5–2.9 秒，说明这台机器的 base 推理在本样本上快于播放，仍不能据此保证“播放后立刻逐字出字幕”。当前边播边识别处理约 20 秒窗口并提前处理约一分钟；未缓存节目会先准备整集音频。本地识别和翻译每批启动独立进程，自动语言检测、失败拆段重试及翻译也会增加时间。强制保活模型虽然能减少初始化，但会增加常驻内存，本轮保留现有任务生命周期。

下一步优先在发行版记录真实节目的“缓存就绪 → 首段字幕可见”时间与长时内存曲线，再决定是否改为增量音频准备或驻留推理进程。另需观察多集字幕的 store 缓存和多个保活页面；当前未做内存泄漏判定或无依据的清理策略变更。
