### 必须马上处理的事（4 件）

1. **堵住"第三方音源脚本 → 本地任意代码执行"**（P0-1、P0-3、P0-5）：引擎页把远程音源包 `import` 进自己的 JS 运行环境，而该窗口能调用全部 142 个应用命令，其中包括"启动任意 exe"。这是本次审查最严重的结构性问题。
2. **把生产后端从明文 HTTP 换成 HTTPS**（P0-2）：服务器**已经支持 HTTPS**（实测 `https://astral.canace.cn/...` 返回 200），改一行 `app.config.json` + 重编译即可；在改完之前，更新链路的 MD5 校验形同虚设。
3. **拆掉 `main.tsx` 那个"把 `#root` 清空"的兜底**（P0-6）：它监听的是 `unhandledrejection`，而前端有 30+ 处无 `catch` 的裸 `void async()` 调用 —— 任何一次 IPC 失败都会把界面打成不可恢复的红屏。这是投入最小、用户感知最强的一改。
4. **加一条 CI**（P1-6）：仓库目前**零 CI、零 lint/format 配置**，`check-lx-bodies` 这类曾拦住线上事故的守卫只存在于手动命令里。

## 三、P0 安全问题

### P0-1　第三方音源脚本可在本机执行任意代码（最严重）

**证据链（全部经我亲手核对源码，非推断）**

1. `src-tauri/src/source_window.rs:16-39`：音源引擎是一个隐藏 webview，加载 `qtres://localhost/engine/index.html`。
2. `src-tauri/src/source_engine_page.html:22-24`：该页取出 `window.__TAURI_INTERNALS__.invoke` 存为局部变量 —— **但没有删除全局**。
3. 同文件 `:114` / `:123`：**紧接着就 `await import(...)` 把远程/内置音源包拉进同一个 JS 运行环境**：
   ```js
   const mod = await import("/script/" + encodeURIComponent(dir) + "/source-bundle.js");
   ```
   第三方脚本与上面那段 glue 代码共享同一个 `globalThis`，因此 `window.__TAURI_INTERNALS__` 对脚本完全可见。
4. **关键**：Tauri 2.11.5 的命令分发只在三种情况下查 ACL —— `tauri-2.11.5/src/webview/mod.rs:1819-1827`：
   ```rust
   // Check ACL on plugin commands, when the app defined its ACL manifest,
   // or when the request comes from a non-local (remote) origin.
   if (plugin_command.is_some() || has_app_acl_manifest || !is_local)
     && request.cmd != FETCH_CHANNEL_DATA_COMMAND
     && invoke.acl.is_none()
   { /* reject */ }
   ```
   三个条件本项目的取值：
   - `plugin_command` = `None`（`source_state`、`run_update_installer` 等是应用自定义命令，不带 `plugin:` 前缀）；
   - `has_app_acl_manifest` = **false** —— 实测 `src-tauri/permissions/` 目录不存在，`src-tauri/gen/schemas/acl-manifests.json` 的顶层键只有 `core`、`core:*`、`dialog`、`global-shortcut`、`notification`，**没有任何自定义命令的权限条目**；
   - `is_local` = **true** —— `tauri-2.11.5/src/webview/mod.rs:1715-1734` 明确把"用户注册的自定义协议"算作本地来源；Windows 上引擎页被规范化为 `http://qtres.localhost/...`，域名剥掉 `.localhost` 得到 `qtres`，命中 `lib.rs:95` 的 `register_asynchronous_uri_scheme_protocol("qtres", ...)`。
   ⇒ 三个条件全不成立 → **完全不做 ACL 校验，直接分发到应用命令处理器**。

5. `src-tauri/src/lib.rs:238-389` 的 `generate_handler!` 注册了 **142 个**应用命令，其中直接构成危害的包括：
   `run_update_installer`（启动任意路径 exe）、`download_update_file`（任意 URL 落盘）、`source_install`、`delete_local_track(s)`、`delete_download(s)`、`get_local_track_files`、`get_scan_dirs`、`app_restart`…

**影响**：任何能进入音源包的脚本（社区音源包、上游包被投毒、或经 P0-2 明文链路被中间人替换的包）都等同于**在本机拿到应用的全部权限**：写任意文件、删用户文件、枚举磁盘、下载并执行程序。`capabilities/source-engine.json` 里"只允许事件监听/发送"的描述与事实不符 —— capability 只约束插件命令。

**修复（按代价从低到高）**

- **立即（小时级）**：在 `source_engine_page.html` 捕获 invoke 之后、`import` 之前删除全局，并冻结残余入口：
  ```js
  const internals = await waitInternals();
  const invoke = internals.invoke.bind(internals);
  const transformCallback = internals.transformCallback.bind(internals);
  // 必须在 import 任何第三方 bundle 之前执行
  delete window.__TAURI_INTERNALS__;
  ```
  这只挡"直接取全局"这一条路，属于止血而非根治。
- **短期（天级，推荐并行做）**：危险命令加**调用窗口白名单**。Tauri 命令可以注入 `webview: tauri::Webview` 参数：
  ```rust
  #[tauri::command(rename = "run_update_installer")]
  pub async fn cmd_run_update_installer(
      webview: tauri::Webview, app: tauri::AppHandle, path: String,
  ) -> Result<(), String> {
      if webview.label() != "main" { return Err("非法调用来源".into()); }
      // ... 原有逻辑
  }
  ```
  对 `run_update_installer`、`download_update_file`、`source_install`、`delete_local_*`、`app_restart` 等逐一加。同时把"引擎专用"命令（`builtin_request`/`source_state`/`source_report`/`source_mark_bad`）与"主窗口专用"命令拆成两个 `invoke_handler`，从架构上分清权限面。
- **根治（推荐）**：把音源脚本移出带 IPC 的页面 —— 放进 **Web Worker**（无 `__TAURI_INTERNALS__`，且有硬超时 `terminate()` 能力，顺带解决 P1-3），或用独立 webview + `postMessage` 只暴露几个必需消息。这样"脚本能不能调命令"就不再依赖任何命令层的自觉。

### P0-2　生产后端是明文 HTTP，更新链路可被中间人替换成任意程序

**证据**

- `src-tauri/src/app_config.rs:31`（由 `app.config.json:26` 生成）：`PROD_BASE_URL = "http://astral.canace.cn/api/v1/"` —— **http 明文**，且是当前生效值（`backend.active = "prod"`）。
- 实测：`http://astral.canace.cn/api/v1/app/source/manifest?platform=1103` → **HTTP 200**（未跳转 https），说明明文链路是活的、日常在用。
- 实测：`https://astral.canace.cn/api/v1/app/source/manifest?platform=1103` → **HTTP 200**，返回合法 JSON ⇒ **服务器已支持 HTTPS，切换成本≈改一行配置**。
- `src-tauri/src/astral.rs:976-1008` `verify_update_file`：**MD5**（非 SHA-256）校验，且 `expect_md5` / `expect_size` 都是 `Option`，`.filter(|s| !s.is_empty())` ⇒ 后端不下发就**完全不校验**（fail-open）。
- `src-tauri/src/commands.rs:636-655` `run_update_installer`：`std::process::Command::new(&path).arg("/UPDATE").spawn()` 后 900 ms 退出应用 ⇒ 下载完的程序会被**直接执行**，无签名校验。
- 更新地址还可能是第三方加速前缀（`astral.rs:806-820` 的 ghproxy 拼接），而 `tauri.conf.json` 里**没有 `signingIdentity` / updater pubkey**，安装包也无 Authenticode 签名。

**攻击链**：用户在公共 WiFi/被劫持的出口 → 中间人直接应答那份明文 JSON，把 `downloadUrl` 指向恶意 exe 并附上**与之匹配的 `md5`** → 客户端下载、校验通过、启动安装器 → **任意代码执行**。同一链路还能改写 `browserUrl`（配合 P0-5 的命令注入）。

**修复**

1. `app.config.json` 的 `backend.prod` 改 `https://astral.canace.cn/api/v1/`，跑 `pnpm config:sync`，重新发布（服务端证书已就绪）。
2. 客户端把明文彻底关掉：release 构建给 reqwest 加 `.https_only(true)`（dev 走 `http://localhost` 需保留例外，可按 `cfg!(debug_assertions)` 分支）。
3. 校验从 fail-open 改 **fail-closed**：`md5` 换 `sha256`，缺哈希就拒绝安装；并在启动安装器前用 `WinVerifyTrust` 校验 Authenticode 签名；中期改用 `tauri-plugin-updater` + minisign 公钥（Tauri 官方更新机制自带签名校验）。
4. 修完之前，可先把 `backend.active` 切回 `dev` 或临时关掉自动更新检查，避免明文链路继续生效。

### P0-3　音源包安装存在路径穿越 → 任意路径写入

**证据**（我亲手核对）`src-tauri/src/source_install.rs:319-341`：

```rust
let target = install_dir(&dir, release.source_version_code);
std::fs::create_dir_all(&target)?;
for artifact in &release.artifacts {
    files.insert(artifact.path.clone(), artifact.version);
    let local = target.join(&artifact.path);        // ← artifact.path 来自远端 manifest，未做任何校验
    ...
    let bytes = download_file(&artifact.url, 30_000).await?;   // ← url 同样来自 manifest
    std::fs::write(&local, bytes)?;                 // ← 直接写盘
}
```

`artifact.path` 与 `artifact.url` **同出一份远端 manifest**，`target.join()` 对绝对路径、`..`、`\`、盘符都无防护。对比同仓 `qtres.rs:143-153` 对 `/script` 分发做了段名白名单、`:230-246` 还做了 `starts_with_canonical` 兜底 —— **安装侧完全没有**，属"同一个项目里已有正确范式却没复用"。

**影响**：`path = "..\..\..\..\Users\<u>\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup\x.js"` 之类即可写出临时目录；配合 `url` 任意可控 ⇒ **任意 URL → 任意路径写入**，落入启动目录即为持久化 RCE。结合 P0-2 的明文链路，中间人无需伪造音源包作者身份就能做到。

**修复**：抽一个 `fn safe_artifact_path(root: &Path, rel: &str) -> Result<PathBuf, String>`，规则：拒绝空串/绝对路径/含盘符/含 `\`/任一段为 `..`；扩展名白名单（`.js` / `.json`）；最后复用 `qtres.rs:230` 的 `starts_with_canonical` 做前缀兜底。同时对 `artifact.url` 强制 `https` + host 白名单。并补一个"恶意 manifest"表驱动单测。

### P0-4　`builtin_request` 是无限定的出网代理，且直接暴露给第三方脚本

**证据**

- `src-tauri/src/commands.rs:48-117` `source_builtin_request`：`url`、`method`、`headers`、`body`、`timeoutMs` **全部由调用方给定**，无 scheme 限制、无 host 白名单、无内网/回环拦截，返回完整响应体。
- `src-tauri/src/source_engine_page.html:87-91`、`:202-206`：把它作为 `request` 注入音源 bundle。

**影响**：这是绕过 CSP（`tauri.conf.json:29` 的 `connect-src 'self' ipc: ...`）的一条**完整 SSRF / 数据外泄通道** —— 脚本可请求 `http://127.0.0.1:27000`（本机 astral 后端）、`http://qtres.localhost/`、局域网设备，可自带任意请求头（包括把 satoken 打给外部地址），并把内网响应回传出去。配合 P0-1，第三方脚本天然拥有这条通道。

**修复**：`source_builtin_request` 内做三层校验 —— scheme 只允许 `http`/`https`；解析后拒绝回环、私有网段、链路本地地址（`127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`::1`）；host 走音源域名白名单（可复用 `qtres.rs:26-43` 的 `ALLOWED_HOST_SUFFIXES` 思路，注意下面 §9.2 说的后缀匹配陷阱）。另外限制 method 集合与 body 大小，并按窗口 label 区分"主窗口代发"与"引擎页代发"两种命令。

### P0-6　"白屏兜底"本身会把应用打成不可恢复的红屏（前端最该先修的一个）

**证据**（我亲手核对）`src/main.tsx:8-27`：

```js
function showFatalError(message) {
  const root = document.getElementById("root");
  root.innerHTML = "";              // ← 直接把 React 的宿主节点清空
  ... root.appendChild(pre);        // 整窗变成一段红字，且没有任何恢复入口
}
window.addEventListener("error", (e) => showFatalError(...));
window.addEventListener("unhandledrejection", (e) => showFatalError(...));   // ← 关键
```

- 注释写的是"白屏兜底…避免只有空白窗口没有线索"，但它**监听的是 `unhandledrejection`** —— 任何一处未处理的 Promise 拒绝都会走这里。
- 而这类调用在前端**大量存在**：30+ 处形如 `void playQueue(...)`、`void toggle()`、`void setVolume()` 的裸调用（`TrackList.tsx:96/100`、`PlayerBar.tsx:247/630/654` 等），`services/ipc.ts` 里 129 个 `invoke(` 只有 1 个 `try {`。
- 于是：音源引擎还没就绪、某条命令返回 `Err`、纯 `vite dev` 下没有 Tauri 环境……任何一种都会触发 `unhandledrejection` → `innerHTML = ""` → **整个界面被销毁**，用户只能杀进程；而且此时 React 树已经被摘掉，连"重试"都不可能。

**影响**：这是"前端体验最差的一条"，它把任何一个本可降级的小错误放大成"应用砖掉"。叠加 P0-7 那个会真抛 `TypeError` 的 setter，触发路径是现成的。

**修复**

### P0-7　快捷键设置页会写坏用户配置，并且有一个 setter 会真抛异常

**证据**（我亲手核对 `src/components/SettingsPage.tsx`）

**问题 A：Esc 会被存成快捷键，而界面写着"Esc 取消"**

```js
// :949-967 录制监听（capture 阶段）
const onKey = (e) => {
  e.preventDefault(); e.stopPropagation();
  if (["Control","Shift","Alt","Meta"].includes(e.key)) return;   // :955 排除列表里没有 Escape
  const keyName = e.key.length === 1 ? e.key.toUpperCase() : e.key; // "Escape"
  parts.push(keyName);
  setDraft((d) => ({ ...d, [listening]: { ...d[listening], key: parts.join("+") } })); // :962 → key: "Escape"
  setListening(null);
};
window.addEventListener("keydown", onKey, true);                   // capture=true
```

- capture 阶段先跑，并且 `preventDefault() + stopPropagation()`，因此输入框自己的 `onKeyDown`（`:1036-1038` 的 `if (ev.key === "Escape") setListening(null)`）**永远收不到事件 —— 是死代码**。
- 界面文案 `:1026` 明确写着"按下新的快捷键组合（Esc 取消）…"，与实际行为完全相反。
- 后果：用户按 Esc 想取消，结果**把该动作的快捷键设成了 `Escape`**（还会继续走到"保存"写进配置）。

**问题 B：Switch 的 setter 没有 `?? ` 兜底，可抛 `TypeError`**

```js
// 渲染处 :1018 有兜底
const d = draft[e.id] ?? { key: e.accelerator, enabled: e.enabled };
// setter :1048-1053 没有兜底
setDraft((prev) => ({ ...prev, [e.id]: { ...prev[e.id], enabled: !prev[e.id].enabled } }));
```

而 `save()`（`:969-980`）成功后**只 `setEntries(list)`，不重建 `draft`**（对比 `reset()` 在 `:991-993` 是有重建的）。因此只要后端返回的 `entries` 里出现 `draft` 中没有的 id（新增动作、后端加了字段、或保存后 id 集合变化），切一下开关就是 `Cannot read properties of undefined (reading 'enabled')` → 撞上 P0-6 的 `unhandledrejection` 兜底 → **整窗红屏**。

**修复**

1. capture 监听首行加：`if (e.key === "Escape") { setListening(null); return; }`（放在 `preventDefault` 之前更自然）。
2. `save()` 成功后与 `reset()` 一样重建 `draft`（或干脆让 `draft` 由 `entries` 单向派生 + 只记录"脏字段"）。
3. setter 用 `prev[e.id] ?? { key: e.accelerator, enabled: e.enabled }` 兜底，与渲染处保持一致。

## 四、P1 稳定性与正确性问题

### P1-1　`panic = "abort"` × 410 处 unwrap/expect = 无提示闪退

`Cargo.toml:69` 设了 `panic = "abort"`（为压体积，合理），但配合 410 处 `.unwrap()/.expect()`（`db/store.rs` 单文件 177 处、`audio/engine.rs` 48、`local.rs` 40），后果被放大：abort 模式下 `#[tauri::command]` 的 `catch_unwind` 兜底**失效**，一次 Mutex 中毒（如 `db/mod.rs` 的 `self.conn.lock().unwrap()`）、一次序列化失败，就是**进程直接消失** —— 托盘图标、退出清理、播放现场落盘全都不执行，用户只看到"闪退"，且没有日志线索。

**修复**：先把 `panic = "abort"` 改回默认 `unwind`（体积代价很小），让命令层重新有兜底；再把全局 `lock().unwrap()` 收敛为 `unwrap_or_else(|e| e.into_inner())` 或统一转 `thiserror` 错误返回；对确实"不可恢复"的位置保留显式 panic 并加日志。这一步成本最低、立刻把"闪退"降级为"一条错误提示"。

### P1-2　更新包文件名取自 URL，可越出临时目录

`astral.rs:923-928`：`let file_name = url.split('/').next_back()...; let path = dir.join(file_name);` —— 只按 `/` 切分，**反斜杠不参与切分**，因此 `..\..\x.exe` 这类尾段在 Windows 上会越出 `%TEMP%\quietmusic-update`。与 P0-2/P0-5 合起来是"下载到任意位置 + 执行"。

**修复**：固定文件名为 `quietmusic-setup.exe`（更新器不需要保留原始名），或 `Path::new(name).file_name()` 过滤并加 `starts_with_canonical` 兜底。

### P1-3　音源脚本运行期没有任何中断手段（有历史事故佐证）

- `budget.ts:64-65` 注释自述"无 AbortSignal 通道"；`:90-98` 用 `Promise.race` + `setTimeout`，**只是不再等待，不取消底层工作**。
- `play-url.ts:441-450`：并行线路一次性全部起跑，**无并发上限**；每条候选地址还额外发一次 Range 预检（`:244-262`）。
- `bridge.ts:288-295`：`init` 是**同步执行**且无超时 —— 脚本里一个同步死循环就能冻结整个引擎页。
- `scripts/build-sources.mjs:85-92`、`restore-lx-bodies.mjs:4-13` 明确记录了 **2026091905 事故**：脚本自校验退化成同步忙循环，冻结事件循环。目前的唯一拦截是**构建期**的 `check-lx-bodies.mjs`（Node Worker 看门狗），属"出厂体检"，**运行期仍无防护**。

**修复**：把脚本执行放进 Worker 并设硬超时 `terminate()`（复用 `check-lx-bodies.mjs` 的看门狗思路）；给 `RequestBuiltin` 增加 signal/取消字段贯通到 Rust（reqwest 可 abort），`budget` 超时即 abort；给并行线路加并发上限（2~3）。

### P1-4　聚合类动作串行且无单项超时，慢源可拖满整个 RPC

`aggregate.ts:73-80 / 112-119 / 126-136`：`allSearchBatches`、`allCharts`、`allHotWords` 都逐个 `await`，只 try/catch 跳过失败、**无 per-source 超时**；而客户端 `INVOKE_TIMEOUT_MS` 只有 20s（`client.ts:77`）。任一平台挂死即吃满自身 15s 超时（`host-request.ts:19` 默认 `timeoutMs: 15000`，而整链预算只有 5s）—— 四源串行最坏直接触发客户端超时，用户看到**空结果**而不是部分结果。对比 `index.ts:464-491` 同一需求用了 `Promise.all` + perSource 计算，同一套聚合存在**两份实现**。

**修复**：统一改 `Promise.allSettled` + 每项 3~4s 独立超时；把 `index.ts` 与 `aggregate.ts` 的重复聚合合并成一份；`host-request` 默认超时收敛到不超过单线路预算。

### P1-5　前端没有任何 ErrorBoundary

实测全仓 `ErrorBoundary` / `componentDidCatch` / `getDerivedStateFromError` 命中数为 **0**。`main.tsx` 虽有全局处理，但它监听的是 `error` 与 `unhandledrejection`，而且处理方式是**清空 `#root`**（见 P0-6）—— 也就是说当前策略不是"兜住局部错误"，而是"一有未捕获错误就把整个 UI 换掉"。对桌面应用而言这是"用户只能杀进程"的体验，现场信息（哪个组件、什么数据）也会随 React 树一起丢掉。

**修复**：在路由层（`AppShell` 内、`KeepAliveOutlet` 外侧）加顶层 ErrorBoundary：渲染错误卡片 + "重载界面"按钮 + 把 `componentStack` 写日志（复用已有的 `app.lastError` 落库通道）；对已知脆弱区域（`LyricWindow`、`SettingsPage` 各页签、`KeepAliveOutlet` 的每个常驻页）再包一层局部边界 —— 尤其 KeepAlive 场景，单个页面崩掉不应连累其它 9 个常驻页。

### P1-6　仓库零 CI，质量门禁全靠人记

实测 `.github/` 不存在，无 `.gitlab-ci.yml`、无 Jenkins/Azure/Circle 配置（`git ls-files` 里唯一 yml 是 `pnpm-lock.yaml`/`pnpm-workspace.yaml`）。`docs/PACKAGING.md:36` 写了 `clippy -D warnings`，**但没有任何东西执行它**。后果是：`check-lx-bodies` 这类曾拦住线上事故的守卫、`config:check`、`tsc`、120 个 Rust 单测，全部只在你手动敲命令时才有意义（详见 P1-7、P3-1 的产物漂移）。

**修复**：加一个 Windows runner 的最小 workflow：
`config:check` → `tsc --noEmit` → `vitest run` → `cargo fmt --check` → `cargo clippy -- -D warnings` → `cargo test --lib` →（可选）`build:sources` 后与已提交的 `builtin-sources/` 逐字节 diff，不一致即失败。

### P1-7　构建期守卫不在 `test`/`build` 里

`package.json:8-12`：`build` = `sync-config && tsc --noEmit && vite build`，`test` = `sync-config --check && vitest run` —— **都不包含** `build:sources`、`check-lx-bodies`、产物一致性校验。也就是说 2026091905 那类"bundle 能 import 但脚本 init 会挂死"的缺陷，可以再次顺利通过 `pnpm test` 和 `pnpm build` 发布出去。

**修复**：把 `check-lx-bodies` 挂进 `test`（或独立 CI job），并对 `builtin-sources/source-bundle.js` 加哈希留痕与一致性校验。

### P1-8　前端请求零取消能力；`usePagedList` 的真实问题不是竞态而是渲染期写状态

**先纠正一个容易误判的点**：`usePagedList` 的竞态防护**其实是对的** —— `hooks/usePagedList.ts:84-92` 有 `cancelled` 标志，`:98` 与 `:108` 在 `await` 之后各自 `if (cancelled) return`，`resetKey` 变化经 `:78-81` 归位。也就是说**快速切页不会出现"旧结果覆盖新列表"**（这一点可以放心，不必大改）。

真正的问题是三个：

1. **整个前端没有任何取消能力**：实测 `new AbortController` / `.abort()` 全仓 **0 处**。`cancelled` 只是"丢弃结果"，底层 IPC/网络请求仍会跑完（与 P1-3 的"超时不取消"是同一个病根）。
2. **在渲染期 `setState` / 写 ref**：`:78-81` 在渲染阶段 `setCursor/setView`，`:63-68` 在渲染期写 4 个 `fetchRef.current`。React 并发渲染下，被丢弃的那次渲染会把这些值写坏（典型症状是偶发"页码与实际列表不一致"）。
3. **`appendUnique` 是 O(n²)**：`:269-282` 每追加一页都 `new Set(prev.map(keyOf))` 全量重建 key 集合。`ArtistPage` 的 `mode:"all"` + `maxPages:60` 场景下约 60 次全量扫描。
4. 小问题：`EMPTY_VIEW.hasMore: true`（`:261-267`）会让重置后的首帧短暂显示"还有下一页"。

**修复**：`cancelled` 守卫保留；把 resetKey 归位改成 `key={resetKey}` 强制重挂（或 `useEffect` + `useReducer`），ref 同步搬进 effect；`appendUnique` 复用同一个累积 `seen` Set（存在 ref 里）避免每页重建；`EMPTY_VIEW.hasMore` 置 `false`；`ipc.ts` 加统一封装，把"调用点卸载/参数变化即作废"变成默认行为。

### P1-9　KeepAlive 常驻页无上限、数据永久陈旧，且隐藏时仍继续轮询

**机制**（我亲手核对 `components/layout/KeepAliveOutlet.tsx`）

- `:26-37` 登记 **10 个**一级页面；`:49-53` **首次访问即 `cacheRef.current.set(path, factory())`**（注意是在**渲染期**写 ref），`:56-69` 非当前页只做 `style={{display:"none"}}` + `aria-hidden` —— **组件永不卸载**，注释也写明"之后一直存活到应用退出"。

**后果**

1. **内存与资源单调增长**：10 个页面的 DOM、store 订阅、`IntersectionObserver`、已加载的封面 `<img>`、分页数据全部常驻到退出；用得越久越重。
2. **数据永久陈旧（无重新校验入口）**：页面只在"首次挂载"拉一次数据 —— `StatsPage.tsx:26-55`（依赖 `[]`）、`MyPlaylistsPage.tsx:35-56`（`pullLikes` 只在首次挂载跑，与 `:23` 注释"打开本页时自动拉取"不符）、`LibraryPage.tsx:80`。于是"听完歌再进 /stats 看不到刚才的播放"、"别端改了歌单再进我的歌单还是旧的"。
3. **隐藏页仍在轮询**：`DownloadsPage.tsx:64-71` 的 1 秒 `setInterval` 只判断 `hasActive`、**不判断页面是否可见**；因为页面从不卸载，用户切到别的页面后它照样每秒打一次 IPC（效果上即"隐藏时轮询"）。

**修复**：给 `KeepAliveOutlet` 注入 `active` 标记（React Context 最简单），各常驻页把"首次挂载加载"改成 `useEffect(() => { if (active) void load(); }, [active, load])` —— 一次改动同时解决"陈旧"和"隐藏轮询"；轮询类 effect 在 `!active` 时直接不注册。若后续页面继续增加，再加 LRU 上限（如最多常驻 5 页）。

### P1-10　播放条每 250ms 全量重渲染

`stores/player.ts:169-193` 的 `applyTick` 每 250ms 执行一次 `set({ state: { ...st, positionMs, durationMs, bufferedMs } })` —— **每次都造一个新对象**，并把 `positionAnchorMs`（`performance.now()`）、`pendingSeekAt` 这类本该是 ref 的值塞进 store；而 `PlayerBar.tsx:46` 与 `:610`（音量控件）都订阅整个 `s.state`。结果是播放条（及其子树）**每秒被重建 4 次**，且与进度无关的部分也跟着重渲染。

**正面**：状态管理整体是干净的 —— 无 `any`、0 处整店订阅、`DownloadButton.tsx:25-26` 用 `s => s.isDownloaded(track)` 这种派生选择器写法正确、跨 store 只有单向 `getState()`（无循环依赖）。

**修复**：把 `positionMs/durationMs/bufferedMs` 从 `state` 快照里拆成独立标量 slice（组件直接订 `s.positionMs`），或用 `useShallow` + 拆分选择器把"高频变化"和"低频变化"分开订阅；`positionAnchorMs`/`pendingSeekAt` 移出 store 改为 ref。

## 五、P2 性能与体积

### P2-1　音源包 44% 是同一批文本的两份拷贝

### P2-2　前端单 chunk + 27 个路由零懒加载

- `vite.config.ts:40-46` 没有 `rollupOptions.output.manualChunks`，且把 `chunkSizeWarningLimit` 抬到 1024（把警告藏了起来）。
- 实测 `lazy(` **0 处**、`createRoute` 等路由定义 **27 处** ⇒ 设置页（`SettingsPage.tsx` 1,232 行）、歌词窗、我的页签等**首屏不需要的代码全部进入同一个 577 KB chunk**，解析/编译成本全压在启动路径上。

**修复**：27 个路由改 `React.lazy` + `Suspense`（TanStack Router 支持 `lazyRouteComponent`）；`manualChunks` 至少把 `react`/`react-dom`/`@tanstack/react-router`/`zustand`/`lucide-react` 拆开，让主包与业务包分离；把 `chunkSizeWarningLimit` 调回默认，让警告重新可见。

### P2-3　长列表没有虚拟滚动

实测无 `react-window`/`virtuoso`/虚拟列表实现。本地音乐库（`LibraryPage.tsx` 625 行）、搜索结果、歌单、下载列表都是全量 `.map` 渲染 —— 几千首本地曲目时首屏 DOM 数量与滚动帧率都会明显劣化（本地库恰恰是"用户自己的文件越多越卡"的典型场景）。

**修复**：列表组件统一走一个虚拟化封装（`@tanstack/react-virtual` 与现有 TanStack 生态同源，体积小），先用在本地库与搜索/歌单/下载四处。

### P2-4　async 命令里做阻塞 IO，会占住 tokio worker

- `astral.rs:915-972` `download_update_file` 是 `async fn`，内部 `std::fs::create_dir_all` / `File::create` / `write_all` / `flush` **全是阻塞调用**，并被 `commands.rs:596-625` 的 async 命令直接 `await`。

### P2-5　无界/半无界缓存

**修复**：`PlayUrlCache` 加 `max_entries`（如 512）并在 `set` 时批量清扫过期项；封面 LRU 换 `lru` crate；`PENDING` 加"同一 track 单飞合并"（并发取链只发一个请求）。

### P2-6　超时预算与默认值语义脱节

整链预算 5s（`budget.ts:23`），但单请求默认 `timeoutMs: 15000`（`host-request.ts:19`、`bridge.ts:182`）—— 脚本不显式传超时时，单请求允许跑满 15s，把"5s 总预算"的语义架空了。**修复**：默认单请求超时收敛到不超过单线路预算（如 3s），并把超时值集中为常量。

### P2-7　`db/store.rs` 单文件混装八套表的 CRUD

`db/store.rs` 约 2,000+ 行、177 处 unwrap/expect，把曲目/歌单/收藏/历史/统计/下载任务/队列/设置八套表的读写混在一起；`db/mod.rs` 是**单 `Mutex<Connection>` 串行**，而 `audio/engine.rs` 会在音频引擎线程内同步写库，与后台 `spawn_blocking` 写库抢同一把锁 —— 表现就是切歌/暂停偶发排队卡顿。**修复**：按域拆 `store/{tracks,playlists,likes,history,stats,downloads,session,settings}.rs`；DB 写入投递到独立写线程（或换连接池 + WAL）。

### P2-8　前端持久化没有版本迁移，外观设置写库失败静默

- `stores/musicSource.ts:45-53`：persist 只配了 `{ name, storage }` —— **没有 `version`、没有 `migrate`、没有 `partialize`**。将来音源相关字段改形状，旧结构会被直接 hydrate 进新代码（Tauri 桌面端用户不会清缓存，这类问题会长期潜伏）。
- `stores/appearance.ts:32-40`：`update` 先 `set({ preference: next })` 再 `await setAppearance(next)`，而 `catch {}` **全吞**。写库失败时界面显示已生效、重启却回滚，用户无从察觉。

**修复**：persist 补 `version` + `migrate` + `partialize`（只持久化必要字段）；`appearance` 的写失败落到可见提示（复用现有 error/notice 位）或进重试队列。

### P2-9　设置页的重复模板与每次渲染重建的常量

- `SettingsPage.tsx:1001-1010`：`LABELS` 定义在组件体内，**每次渲染新建一个对象**（应提到模块顶层）。
- `AboutSection:872-896` 与 `SourcePackageSection` 各自重写了一遍"按钮 + busy/checking + setError + errMsg"的同一套异步动作模板。
- `:774` 的 `window.setTimeout(...)` **没有保存句柄**，组件卸载后仍会 `setMessage`（该页虽常驻，但换页签/触发重挂时是隐患）。

**修复**：`LABELS` 提到模块顶层；抽 `<AsyncActionButton>` 统一 loading/disabled/错误展示；`setTimeout` 存 ref 并在清理里 `clearTimeout`。这个文件 1,302 行、是项目里最大也最常改的前端文件，建议按页签拆子组件（见 §6.7）。

### P2-10　无障碍的"质性"缺口（数字之外）

数字上不差（`aria-*` 105 处、22 个 `<img>` 全部带 `alt`、`outline-none` 都配了 `focus-visible`），但关键的几样都没有：

- **0 处 `aria-live` / `role="status"` / `role="alert"`** ⇒ 所有"保存成功 / 下载完成 / 导入失败"提示对读屏器**完全不可见**。
- **全仓只有 1 个真正的 `role="dialog" + aria-modal`**（`components/notice/qt-NoticeDialog.tsx:83-84`）；`UpdateDialog`、`mine/ImportPlaylistDialog`、`onboarding/OnboardingPage` 三处手写弹窗**都没有** `role`/`aria-modal`/`aria-labelledby`/Escape/焦点陷阱/焦点归还（`autoFocus` 全仓仅 2 处）。
- **队列排序只能拖鼠标**：`player/QueuePanel.tsx:123-148` 只用 HTML5 `draggable`，键盘无法重排。

**修复**：抽一个 `<Modal>` 组件（role/aria-modal/labelledby/Escape/focus trap/归还）替换三处手写弹窗；加一个全局 `aria-live="polite"` 的 toast 容器承载现有提示；队列行加"上移/下移"按钮（复用 `:70/:204` 已有的 `move` 范围守卫）。
