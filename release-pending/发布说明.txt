一、本次改什么（只改 chain.json，bundle 不动）
----------------------------------------------------
依据「逐线路全量重测」（每平台每条线路单独装链、每线路用不同歌曲绕过缓存）
的真实耗时与命中率重排：

qq：墨澜 tx → World260809 → Stellarwave tx → 玉宁熙 tang
    - 墨澜 tx 实测 402-841ms，是 qq 链最快的一条（3 档全通），保持置首
    - 移除 Stellarwave tx 的 parallel：它原本每次取链都并发起跑，
      即使前面已命中也要白跑一遍（QuickJS 单线程上是纯浪费）
    - 实测：12 首不同歌曲全部由墨澜首条命中，平均 542ms（旧链 1017ms）

kw：酷我官方 DES → 玉宁熙 Pro → 屿溪 → 全豆要 → Stellarwave
    - 官方 DES 是 bundle 实现（**不 init 任何混淆宿主**），实测 102-253ms 最快，置首
    - Stellarwave 实测 320/128 档 4168/4701ms（yy.zddyr.top 单请求 4.6s），移到最后

kg：墨澜 → 独家 v6 → Stellarwave → 玉宁熙 Pro → 屿溪
    - 屿溪（原链首）128/320 档实测**死链**（返回地址 Range 预检不过），移到最后
    - 墨澜 412-437ms、独家 v6 239-468ms 是 kg 最快的两条，提前

档内线路数 maxLinesPerQuality：5 → 4
    - 效果正好把两条问题线路挤出执行面：kw-Stellarwave（4.6s）、kg-屿溪（死链）
    - 更重要的是**封住最坏情况**：每条线路都要 init 一个混淆宿主，5 条全跑
      意味着单次取链叠 5 次混淆 init，安卓 QuickJS 上极易撞上引擎的 5s 停用闸门

二、为什么要这样改（安卓「越切越失败」的机制）
----------------------------------------------------
qt-js-engine 的原生侧有一条**事后隔离闸门**（uni_modules/qt-js-engine
utssdk/app-android/index.uts）：

  STALL_MS = 5000        // 单次 evaluate 超过 5s 即判定脚本卡住
  poison(reason)         // 引擎停用：gPoisoned = true
  → 之后所有调用直接失败："引擎已停用，需重启音源引擎"
  → 只能 stop + start 重建（= 用户说的「重启就又可以了」）

而 prelude 的 `__qtPumpAsync()` 在求值 Promise 时会把**微任务队列跑干**——也就是
链路上所有 await 续跑都算在同一次 evaluate 的耗时里。链路每多试一条 LX 线路，
就多一次混淆宿主的同步 init 叠进同一次求值：qq 旧链首条墨澜失败后还有
parallel 的 Stellarwave 并发起跑，kg 旧链 5 条全是混淆宿主 → 单次求值很容易破 5s
→ 引擎停用 → 「QQ 链接经常加载失败」→「最终切换所有歌曲都失败」。

重排后每次取链实际只 init 一个宿主（qq/kg 都是墨澜首条命中，kw 是 bundle 实现
零 init），同步工作量大幅下降，同时整链耗时也从 1017ms 降到 542ms。
